# Техническое задание
## Бот для Max: расчёт натальной и солярной карты

**Платформа выполнения:** локальный сервер на Mac mini (офлайн-совместимый расчётный движок), подключение к каналу Max через Bot API.
**Версия:** 1.0
**Тип документа:** ТЗ для разработчика (в т.ч. AI-агента)

---

## 1. Общая архитектура системы

Система строится по модульному принципу — это ключевое требование, так как в будущем нужно добавлять новые виды расчётов (транзиты, синастрия, прогрессии), новые города, новые языки описаний без переписывания ядра.

### 1.1 Слои приложения

| Слой | Назначение | Технологии (рекомендация) |
|---|---|---|
| Bot Gateway | Приём/отправка сообщений Max, обработка кнопок и меню | Python (aiohttp/FastAPI) + Max Bot API webhook или long polling |
| Диалоговый оркестратор (Dialog Manager) | Состояние диалога, маршрутизация по сценариям (FSM) | Python, конечный автомат состояний на пользователя |
| Модуль клиентских карточек (Client Store) | CRUD карточек клиентов и связанных лиц | SQLite (локально на Mac mini) |
| Расчётное ядро (Astro Engine) | Расчёт натальной карты, соляра, домов, аспектов | Swiss Ephemeris (pyswisseph) |
| Модуль базы городов и времени (GeoTime Service) | Координаты, часовые пояса, история переходов на летнее время | Локальная база (GeoNames + IANA tzdata), с онлайн-докачкой при наличии сети |
| Генератор интерпретаций (Text Composer) | Сборка текстов описаний из шаблонов/базы фраз | Модульная библиотека шаблонов (YAML/JSON) + правила сборки |
| Модуль визуализации (Chart Renderer) | Отрисовка колеса карты в SVG | Python (svgwrite / собственный рендерер) |
| Модуль документов (Export Service) | Формирование .docx с полным описанием | python-docx |
| Модуль "Лучшее место" (Relocation Engine) | Скоринг городов под критерии пользователя | Расчётное ядро + фильтры + кэш результатов |

Все модули взаимодействуют через внутренний API (функции/интерфейсы с чётко типизированными входом/выходом), а не через прямые вызовы друг в друге — это условие модульности и лёгкого добавления новых расчётов в будущем.

### 1.2 Требование к офлайн-работе

Расчётное ядро, база городов/часовых поясов, шаблоны текстов и клиентская база данных должны храниться и работать локально на Mac mini без обращения к интернету. Онлайн-доступ нужен только для: (а) обновления самой программы, (б) докачки новых городов/часовых поясов, (в) получения сообщений из Max (это единственный компонент, которому интернет нужен постоянно, так как канал общения идёт через серверы Max).

## 2. Сценарий 1: Запуск бота и карточка клиента

### 2.1 Приветствие и идентификация

- При первом сообщении от нового Max ID бот отправляет приветственное сообщение и запрашивает имя клиента (если имя не удаётся получить автоматически из профиля Max — запросить текстом).
- Приветствие последующих обращений: "Привет, {имя}!" — без фамилии, даже если фамилия известна.
- Если клиент обращается повторно (Max ID уже есть в базе) — загружается существующая карточка, приветствие персонализировано, бот предлагает продолжить с сохранёнными данными или ввести данные нового человека.

### 2.2 Структура карточки клиента

```
Client
├── client_id (внутренний, uuid)
├── max_user_id (идентификатор в Max)
├── first_name
├── created_at
├── last_active_at
├── settings (языковые/форматные предпочтения, финансовый профиль для адаптивных описаний — опционально на будущее)
└── persons[] — список связанных персон для расчётов
     ├── person_id
     ├── label (например "Я", "Дочь", "Мама" — определяется пользователем свободным текстом)
     ├── full_name (опционально)
     ├── birth_date
     ├── birth_time (с флагом точности: точное/примерное/неизвестное)
     ├── birth_place (город, страна, координаты, часовой пояс на момент рождения)
     └── charts[] — история расчётов
          ├── chart_id
          ├── type (natal / solar)
          ├── computed_at
          ├── input_params (для соляра — год и место встречи)
          ├── result_data (позиции планет, куспиды домов, аспекты — структурированный JSON)
          ├── short_text (сгенерированное краткое описание)
          ├── full_text_path (ссылка на сохранённый .docx)
          └── wheel_svg_path (ссылка на сохранённый SVG)
```

### 2.3 Логика ведения нескольких персон

- В любой момент диалога доступна команда/кнопка "Добавить человека" — создаёт новую запись в `persons[]` под тем же `client_id`.
- При запросе расчёта бот уточняет, для кого он выполняется (если в карточке более одной персоны) — выводит список меток (label) в виде кнопок.
- Изменение данных персоны (дата/время/место) должно быть доступно через меню "Редактировать данные" — не создавая дубликат, а обновляя существующую запись с сохранением истории предыдущих расчётов.

## 3. Сценарий 2: Расчёт натальной карты

### 3.1 Сбор исходных данных

Необходимые поля: дата рождения, время рождения (с явной обработкой случая "время неизвестно" — расчёт по солнечным картам/только знакам без домов, с предупреждением пользователю о неполноте), место рождения (с автодополнением города по базе, см. раздел 6).

### 3.2 Расчёт и сохранение

- Сразу после получения полных данных запускается расчёт натальной карты через Astro Engine (позиции планет, куспиды домов по выбранной системе домов — по умолчанию Placidus, с возможностью смены системы в настройках).
- Результат сохраняется в структурированном виде (JSON) в карточке клиента — это первичный источник для всех дальнейших текстов и визуализаций, чтобы не пересчитывать при каждом запросе.
- Автоматически генерируются: краткое описание, полное описание, документ .docx с полным описанием.

### 3.3 Форматы вывода

| Формат | Содержание | Формат файла |
|---|---|---|
| Короткое описание | Сплошной текст 150-300 слов, ключевые показатели (Солнце, Луна, Асцендент, доминирующие планеты, 2-3 значимых аспекта) | Текст в чате |
| Полное описание | Разбор всех 10 планет по домам и знакам, всех 12 домов, значимых аспектов | Текст в чате (по частям) или предпросмотр |
| Скачиваемая версия | Полный текст с оформлением (заголовки, разделы по планетам/домам) | .docx |

## 4. Сценарий 3: Меню после расчёта натальной карты

После вывода ключевых положений показываются кнопки:

- **Колесо** — отрисованная натальная карта (SVG), отправляется как изображение.
- **Описание** — подменю: короткое / полное / скачать (.docx).
- **Рассчитать соляр** — переход в сценарий 4.
- **Лучшее место** — переход в сценарий 5.
- **В начало** — возврат в главное меню/выбор персоны.

### 4.1 Отрисовка колеса (Chart Renderer)

- Круговая диаграмма 12 домов со знаками зодиака по внешнему кольцу, символами планет в соответствующих домах, линиями аспектов внутри круга.
- Рендерится в SVG (векторный формат — не теряет качество при печати и масштабировании), при отправке в Max конвертируется в PNG нужного разрешения.
- Стилизация (цвета, шрифты, логотип/водяной знак) выносится в отдельный конфигурационный файл темы — это позволяет менять визуальный стиль без изменения кода рендерера.

## 5. Сценарий 4: Расчёт солярной карты

### 5.1 Отличие от натальной карты

Соляр — карта на момент точного возвращения Солнца в его натальный градус, рассчитывается на конкретный год и **конкретное место**, где человек планирует встретить (либо уже встретил) день рождения — это принципиально отличает соляр от натальной карты и требует отдельного запроса геоданных.

### 5.2 Логика сценария

1. Бот запрашивает место встречи соляра (город, с автодополнением из базы городов).
2. Запрашивает год, если не очевиден из контекста (по умолчанию — предстоящий или текущий год ближайшего дня рождения).
3. Astro Engine рассчитывает точный момент возврата Солнца (UTC), пересчитывает карту домов на заданные координаты.
4. Результат сохраняется в `charts[]` карточки персоны с типом `solar`, привязкой к году и месту.
5. Генерируются короткое и полное описания, полное — сохраняется в .docx.
6. Выводится то же меню, что и для натальной карты (колесо, описание, лучшее место, в начало), плюс возможность рассчитать соляр повторно для другого места/года без потери истории предыдущих расчётов.

## 6. Модуль "Лучшее место" (Relocation Engine)

### 6.1 Назначение

Поиск оптимальных для встречи дня рождения географических точек — таких, где положения домов относительно натальных планет создают наиболее благоприятную структуру соляра, либо (для уже прошедшего дня рождения) — анализ эффекта места, где он был встречен, и подбор компенсирующих мер.

### 6.2 Алгоритм

1. Для заданной даты дня рождения перебираются кандидаты-города из базы (см. раздел 7).
2. Применяются пользовательские фильтры (страна, регион, визовый режим, часовой пояс) для сокращения выборки перед расчётом — это критично для скорости при большой базе городов.
3. Для каждого прошедшего фильтр города выполняется расчёт соляра и скоринг по заданным правилам (усиление "желаемых" домов/аспектов, избегание "проблемных" сочетаний — правила скоринга формализуются в отдельной конфигурации, редактируемой без изменения кода).
4. Результаты ранжируются, топ-N городов выводится пользователю с кратким объяснением, почему место хорошее (1-2 предложения на город).
5. Функция "эффект прошедшего места" — пользователь указывает город, где встретил день рождения; система рассчитывает фактический соляр и формирует блок "меры компенсации" — краткие рекомендации по нейтрализации выявленных сложных аспектов/домов.

### 6.3 Производительность

Необходимо тестирование: замер времени полного скоринга по всей базе городов без фильтров. Если время превышает приемлемый порог для отклика бота (рекомендуется ориентироваться на 3-5 секунд ожидания как максимум для пользователя), то фильтрация по стране/визовому режиму становится обязательным первым шагом, а не опциональным. Результаты повторных запросов на одинаковые параметры кэшируются.

## 7. Модуль базы городов и времени (GeoTime Service)

- Источники данных: база координат городов (например, GeoNames), база часовых поясов с историей изменений (IANA tz database), которые нужно адаптировать в локальный формат при первом запуске программы.
- Функция автодополнения при вводе города — подсказки по первым буквам, показ страны для устранения неоднозначности одноимённых городов.
- Обработка городов без точных исторических данных о часовом поясе: подстановка ближайшего города с известными данными в той же стране/часовом поясе, расчёт через смещение по расстоянию/долготе.
- Настройка режима расчёта: истинное солнечное время либо время по часовому поясу — выбирается пользователем в настройках или задаётся системным умолчанием.
- Модуль строится как отдельный сервис с собственным API (`get_coordinates(city)`, `get_timezone_history(city, date)`), чтобly город можно было заменить/расширить новой базой без изменения кода, вызывающего этот сервис.

## 8. Генератор интерпретаций (Text Composer)

Это ядро текстовой части системы, вынесенное в отдельный модуль намеренно — чтобы объём и стиль текстов можно было наращивать без изменения расчётной логики.

### 8.1 Принцип построения

- Тексты строятся не как единый монолитный шаблон на каждую комбинацию, а как сборка из атомарных блоков: `планета × знак`, `планета × дом`, `дом × куспид-знак`, `аспект × пара планет`, с последующей склейкой связующими фразами.
- Для каждого атомарного блока в базе хранится 3-5 вариантов формулировки (используются по ротации/случайному выбору), чтобы тексты разных клиентов не были идентичны при одинаковых показателях — это снижает "шаблонность" и повышает уникальность.
- Итоговый текст пропускается через слой пост-обработки: упрощение синтаксиса (сокращение причастных/деепричастных оборотов), проверка на естественность звучания.

### 8.2 Структура базы текстовых блоков

```
templates/
├── planets_in_signs/       # 10 планет × 12 знаков = 120 комбинаций
├── planets_in_houses/      # 10 планет × 12 домов = 120 комбинаций
├── house_cusps_in_signs/   # 12 домов × 12 знаков = 144 комбинации
├── aspects/                # мажорные аспекты между парами планет
├── solar_specific/         # блоки, специфичные для соляра (акцент на годовой период)
├── connectors/             # связующие фразы для склейки блоков в цельный текст
└── relocation_notes/       # шаблоны объяснений для модуля "Лучшее место"
```

Формат хранения — YAML или JSON с полями `id`, `variants[]`, `tone_tags` (для будущей адаптивности текста под аудиторию, см. п. 8.3).

### 8.3 Адаптивность текста (заложить архитектурно на будущее)

Хотя в данном ТЗ адаптация под финансовый/социальный профиль клиента не входит в первую версию, структура базы текстов должна с самого начала поддерживать поле `tone_tags` у каждого блока (например, `neutral`, `for_budget_conscious`, `for_high_income`), чтобы в будущих версиях можно было подключить логику выбора нужного варианта без переписывания базы текстов.

### 8.4 Порядок генерации короткого и полного текста

1. Расчётное ядро отдаёт JSON с позициями и аспектами.
2. Text Composer выбирает значимые точки для короткого текста (Солнце, Луна, Асцендент, MC, до 3 самых сильных аспектов) и склеивает их в связный абзац через коннекторы.
3. Для полного текста Text Composer проходит по всем планетам, всем домам и всем найденным аспектам последовательно, формируя разделы с подзаголовками.
4. Экспорт полного текста в .docx происходит через отдельный Export Service, использующий уже готовый текст (без повторного обращения к расчётному ядру).

## 9. Хранение данных: рекомендации по оптимизации

- Локальная БД — SQLite: достаточна для одного локального инстанса на Mac mini, не требует отдельного сервера БД, легко резервируется копированием файла.
- Разделение хранения: структурированные данные (карточки, параметры расчётов, позиции планет) — в БД; сгенерированные файлы (.docx, .svg/.png) — в файловой системе, в БД хранятся только пути к ним.
- Кэш повторных вычислений: если пользователь запрашивает пересчёт с теми же входными параметрами, что уже есть в `charts[]`, — расчёт не повторяется, отдаётся сохранённый результат.
- Индексация по `max_user_id` для быстрого доступа к карточке при каждом входящем сообщении.
- Регулярное резервное копирование БД и файлового хранилища (например, ежедневный локальный бэкап на Mac mini на отдельный диск/папку Time Machine).

## 10. Модульность и расширяемость (сквозное требование)

Каждый из следующих компонентов должен быть заменяемым/дополняемым независимо от остальных:

- **Новые виды расчётов** (транзиты, прогрессии, синастрия, дирекции): добавляются как новые типы в `charts[].type`, с собственным модулем расчёта, подключаемым к тому же Astro Engine и тому же Text Composer через единый интерфейс входа/выхода.
- **Новые города/базы часовых поясов**: обновление файлов GeoTime Service без изменения остальной программы.
- **Новые языки описаний**: база текстовых блоков организована по языковому префиксу папки (`templates/ru/`, `templates/en/`), выбор языка — параметр запроса.
- **Новые правила скоринга для "Лучшего места"**: хранятся в отдельном конфигурационном файле правил, редактируемом без пересборки программы.
- **Обновления бота**: локальное приложение должно проверять обновления с внешнего репозитория (например, GitHub) при наличии интернета и применять их без потери локальной базы клиентов.

## 11. Открытые вопросы для уточнения перед началом разработки

- Система домов по умолчанию (Placidus/Koch/Equal и др.) и нужна ли пользователю возможность её менять.
- Формат хранения времени рождения при неизвестном времени: показывать ли карту "на полдень" с явным предупреждением или отказываться от расчёта домов.
- Требуется ли многоязычность в первой версии или только русский.
- Нужна ли пользователю возможность экспортировать не только .docx, но и PDF.
- Критерии скоринга для "Лучшего места" — нужен отдельный список "желаемых эффектов" и "негативных сочетаний домов/планет", который пользователь должен предоставить как содержательный вход для настройки правил (это экспертная астрологическая часть, не техническая).
