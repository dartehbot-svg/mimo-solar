# Часть I. Доработка функциональности бота

## Замечание 1: Выбор персоны из сохранённых профилей для расчёта

### Текущая проблема
Профиль можно сохранить (`/profile_add`, таблица `persons`), но нет сценария, который использует сохранённые данные персоны для запуска расчёта — пользователь каждый раз вводит дату/время/город заново.

### Требуемое поведение

1. При нажатии "Натальная карта" или "Соляр" из стартового меню бот сначала проверяет, есть ли у пользователя сохранённые персоны (`GET /api/users/{id}/persons`).
2. Если персон 0 — обычный сценарий ввода данных (как сейчас), с предложением сохранить введённые данные как новую персону по завершении.
3. Если персон 1 или больше — показывается инлайн-меню выбора:

```
Для кого рассчитать карту?
┌──────────────────┐
│  Я (Иван)        │
│  Мама            │
│  Дочь            │
├──────────────────┤
│  + Новый человек  │
└──────────────────┘
```

4. При выборе существующей персоны — бот сразу переходит к расчёту, используя `birth_date`, `birth_time`, `latitude`, `longitude` из записи `persons`, без повторного запроса.
5. При выборе "+ Новый человек" — запускается стандартный сценарий ввода с последующим предложением сохранить как персону (с запросом метки/label: "Как назвать эту запись? Например: Я, Мама, Дочь").
6. Аналогичное меню выбора персоны должно появляться в сценарии "Лучшее место" и при повторном запросе соляра для уже рассчитанной ранее персоны.

### Технические изменения

- `bot/src/state.ts` — добавить состояние `awaiting_person_selection` с сохранением выбранного `person_id` в `UserState.data`.
- `bot/src/bot.ts` — новая функция `showPersonSelector(userId)`, вызывается перед стартом сценариев natal/solar/bestplace.
- `bot/src/api.ts` — использовать существующий эндпоинт `GET /api/users/{id}/persons` (уже есть в API, не задействован в диалоге).
- После расчёта результат должен сохраняться в `charts` со ссылкой на выбранный `person_id`, а не только в устаревшую таблицу `profiles`.

## Замечание 2: Меню выбора типа описания (натал/соляр) после любого расчёта

### Текущая проблема
Кнопка "Описание" всегда выдаёт описание натальной карты, даже если пользователь только что рассчитал соляр и стоит в контексте соляра.

### Требуемое поведение

1. Кнопка "Описание" в любом контексте (после натала, после соляра, после лучшего места) открывает промежуточное меню выбора, **если для данной персоны рассчитаны оба типа карт**:

```
Описание какой карты показать?
┌──────────────────┬──────────────────┐
│  Натальная карта │      Соляр       │
└──────────────────┴──────────────────┘
```

2. Если рассчитан только один тип (например, соляр ещё не считали) — меню выбора пропускается, показывается описание доступного типа, но с явным ярлыком в заголовке ("Описание натальной карты" / "Описание соляра {год}, {город}"), чтобы пользователь всегда видел, что именно смотрит.
3. После выбора типа карты — обычное подменю "Краткое / Полное", как сейчас, но с учётом выбранного типа.
4. Если у персоны несколько рассчитанных соляров (разные года/города) — при выборе "Соляр" в описании показывается список для выбора конкретного расчёта (год + город), а не только последний.

### Технические изменения

- `bot/src/bot.ts` — функция `showDescriptionTypeSelector(userId, personId)`, проверяющая наличие charts type=natal и type=solar через `GET /api/persons/{id}/charts`.
- Заголовок описания формируется по шаблону: `"{Тип карты} — {Имя персоны}, {дата рождения / соляр год-город}"`.
- Состояние `UserState.data.description_chart_id` — явно хранит, какой именно расчёт (`chart_id`) сейчас показывается, чтобы кнопки "Краткое/Полное/Скачать" работали с правильным расчётом.

## Замечание 3: Расширение описательного блока — аспекты и другие значимые показатели

### Анализ: что важно добавить

В текущей структуре (`interpretations.json`) уже есть блок `aspects` (5 типов между планетами), но в **полное** описание аспекты попадают только "по планете" (до 3 аспектов на планету), а отдельного целостного блока по важнейшим взаимосвязям карты нет. Также не описываются: аспекты к ASC/MC, стеллиум (скопление планет в одном знаке/доме), ретроградность как отдельный смысловой блок, распределение по стихиям/качествам (для более целостной картины личности).

### Требуемая структура полного описания (обновлённая)

1. Вступление (как сейчас).
2. Планеты по одной (знак + дом + ретро) — как сейчас.
3. **Новый блок: "Ключевые аспекты карты"** — не только "аспекты внутри описания планеты", а отдельный раздел с полным списком мажорных аспектов (соединение, секстиль, квадратура, тригон, оппозиция) между всеми парами планет, отсортированный по значимости (точность аспекта — чем меньше орб, тем выше в списке; вес по типу планет из `planet_weights`).
4. **Новый блок: "Асцендент и Середина неба"** — не просто позиция, а какие планеты образуют аспект к ASC/MC (это важные точки, аспекты к которым сильно влияют на самоощущение и карьерный вектор, но сейчас не описываются вообще).
5. **Новый блок: "Особые конфигурации"** (опционально, если найдены):
   - Стеллиум — 3+ планеты в одном знаке или доме;
   - Ретроградные планеты — сводный список с кратким смыслом ретроградности для каждой;
   - Распределение по стихиям (огонь/земля/воздух/вода) и качествам (кардинальные/фиксированные/мутабельные) — краткий вывод о балансе/дисбалансе.
6. Для соляра — дополнительно раздел **"Наложение на натальные дома"** (в описании должно быть явно объяснено, в какие натальные дома попадают планеты соляра и что это означает для года — это уже рассчитывается в `solar.py`, но не выводится текстом).
7. Заключение (как сейчас).

### Что добавить в базу текстов (`interpretations.json`)

```json
{
  "aspects_to_angles": {          // аспекты планет к ASC/MC — 10 планет × 2 точки × 5 аспектов
    "sun_asc_conjunction": {"short": "...", "full": "..."}
  },
  "stelliums": {                   // текст про скопление планет по знакам/домам
    "by_sign": {"овен": "..."},
    "by_house": {"1": "..."}
  },
  "retrograde_summary": {          // краткий смысл ретроградности по планете
    "mercury": "...", "venus": "..."
  },
  "element_balance": {             // тексты по балансу стихий
    "fire_dominant": "...", "water_lacking": "..."
  },
  "solar_house_overlay": {         // наложение планет соляра на натальные дома
    "sun_in_natal_house_10": {"short": "...", "full": "..."}
  }
}
```

### Приоритизация (что важно, а что можно отложить)

| Блок | Важность | Причина |
|---|---|---|
| Полный список мажорных аспектов | Высокая | Ключевая астрологическая информация, сейчас урезана до 3 на планету |
| Наложение соляра на натальные дома | Высокая | Уже считается в коде, но не выводится — быстро добавить |
| Аспекты к ASC/MC | Средняя | Значимо для полноты, но требует новых текстовых блоков |
| Стеллиумы | Средняя | Встречаются не у всех, но при наличии — сильный смысловой акцент |
| Ретроградность (сводно) | Низкая-средняя | Уже упоминается при описании планеты, сводный блок — дополнение |
| Баланс стихий/качеств | Низкая | Полезное дополнение, не критичное для MVP доработки |

Рекомендация: в первую итерацию включить полный список аспектов и наложение соляра (уже есть данные, не хватает только текста и вывода), остальное — во вторую итерацию.

## Замечание 4: Имя скачиваемого файла

### Текущая проблема
Файл описания скачивается с автогенерированным именем (вероятно UUID/hash), телефон интерпретирует расширение как установочный пакет, а не документ — пользователь не понимает, что это.

### Требуемое поведение

Имя файла формируется по шаблону:

```
{Тип карты} {Имя персоны} {дата рождения}.pdf
```

Примеры:
- `Натальная карта Иван 15.03.1990.pdf`
- `Соляр Иван 2027 Сочи.pdf`

### Технические детали реализации

1. Транслитерация/очистка имени не нужна для кириллицы — MAX и большинство мобильных ОС поддерживают кириллицу в именах файлов, но необходимо убрать символы, недопустимые в именах файлов (`/ \ : * ? " < > |`), заменив их на пробел или дефис.
2. Ограничить длину итогового имени файла (рекомендуется до 100 символов) с обрезкой имени персоны при необходимости.
3. При отправке файла через MAX Bot API явно указывать `filename` в параметрах загрузки/отправки документа (в текущей реализации, судя по документации, `pdf_generator.py` возвращает файл через `POST /api/generate-pdf` — необходимо проверить, передаётся ли `Content-Disposition` с корректным именем, либо это тот момент, где имя "съедается" и подставляется временное).
4. Проверить на стороне `bot/src/api.ts` и `bot/src/bot.ts`: при пересылке файла от Core API в MAX бот должен передавать явное имя файла в параметре отправки документа, а не полагаться на дефолтное имя, приходящее от FastAPI/axios (это наиболее вероятная причина текущей проблемы — временное имя формируется автоматически при потоковой передаче байтов без явного указания `filename`).
5. То же правило имени применить и к SVG/PNG колесу карты при скачивании: `Колесо натальной карты Иван 15.03.1990.png`.

### Проверка после исправления
Убедиться на реальном устройстве (iOS и Android в MAX), что файл после скачивания отображается с читаемым именем и открывается как документ, а не предлагается к "установке".

Учитывая, что доработки этого ТЗ добавляют больше шагов в диалоге (выбор персоны, выбор типа описания), рекомендуется перенести `UserState` в SQLite уже на этом этапе, а не откладывать — иначе возросшая сложность сценариев увеличит риск потери контекста при сбоях.

5. **Название файла для будущих типов расчётов** (транзиты, синастрия — см. TODO в документации) — заложить общий генератор имени файла `build_filename(chart_type, person_name, date_or_period)` как отдельную функцию, чтобы не дублировать логику для каждого нового типа расчёта.

# Часть II. Расширение базы городов (замена cities.json на 168 записей)

Текущая база городов (`core/data/cities.json`, 168 записей) минимальна и не удовлетворяет требованиям по полноте для натальной карты и по разделению режимов для соляра. Ниже — детальная структура замены.

## 1. Источники данных

- **GeoNames** — открытая база более 11 млн географических объектов, включает координаты, население, административное деление, коды стран[cite:69][cite:78]. Для практических целей подходит выгрузка "cities with population > 1000" (~200 тыс. записей) или её отфильтрованные версии по порогу населения[cite:65][cite:68].
- **IANA tz database (tzdata)** — эталонная база часовых поясов, хранит не только текущие правила, но всю историю изменений смещений UTC и переходов на летнее время с 1970 года для каждого региона[cite:66][cite:70][cite:76]. Обновляется несколько раз в год при изменении часовых правил в мире (последнее актуальное обновление — 2026c)[cite:73].
- Для регионов РФ существуют отдельные пояса с учётом местных смещений (например, Asia/Barnaul для Алтайского края), которые не совпадают с соседними областями — это нужно учитывать отдельно, не считая всю Сибирь одним поясом[cite:73].

Обе базы скачиваются один раз при разработке, адаптируются в локальный формат (SQLite-таблицы, замена текущего `cities.json`) и работают полностью офлайн на Mac mini. Обновление баз — по необходимости, вручную или через плановое обновление программы.

## 2. Структура списков городов

Создаются **четыре** логических набора данных (один общий пул + три производных "вида" для разных сценариев использования), а не четыре отдельные копии — это экономит место и упрощает поддержку и согласуется с существующей модульной архитектурой (`core/src/timezone_utils.py`, обновление данных без изменения остального кода).

### 2.1 Базовый пул данных (Master Pool)

Единая таблица городов (замена `cities.json`), куда входят все объекты, которые в принципе могут понадобиться. Каждая запись содержит:

```
city_id, name, name_ru, alt_names[], country_code, admin1 (регион/область),
latitude, longitude, population, timezone_id (ссылка на IANA tz),
tier (категория для фильтрации, см. ниже)
```

Поле `tier` — это метка категории города, по которой строятся три производных списка без дублирования данных.

### 2.2 Категории (`tier`) и правила отбора

| Tier | Описание | Критерий включения |
|---|---|---|
| 1 | Столицы всех стран мира | Административный статус "capital" |
| 2 | Крупные города мира (не столицы) | Население выше порога (например, >500 000) |
| 3 | Города РФ | Все населённые пункты РФ с известными координатами, вплоть до малых (для натальной карты нужна максимальная точность места рождения) |
| 4 | Города стран СНГ | Все населённые пункты СНГ с известными координатами |
| 5 | Крупные города/столицы соседних для поездок стран | Подмножество Tier 1/2, ограниченное списком стран с открытым/упрощённым визовым режимом для гражданина РФ (список стран задаётся в конфигурации и может обновляться отдельно от базы городов) |

### 2.3 Три производных списка (для целей задачи)

| Список | Назначение | Состав по tier | Используется в сценарии |
|---|---|---|---|
| **Список A — Натальная карта** | Максимальная полнота для точности места рождения | Tier 1 + 2 + 3 + 4 | Ввод города рождения (натал и профили персон) |
| **Список B — Соляр, полный режим** | То же самое, что список A | Tier 1 + 2 + 3 + 4 | Ввод города встречи соляра (по запросу пользователя — "искать по всему миру") |
| **Список C — Соляр, укороченный режим** | Быстрый выбор из крупных центров | Tier 1 + 2 (либо + крупные города РФ/СНГ выше порога) | Быстрый ввод города соляра по умолчанию |
| **Список D — Соляр, "доступные поездки"** | Быстрый практичный выбор для реального планирования дня рождения | Tier 3 (отфильтрованные по населению) + Tier 5 | Сценарий "Лучшее место" — по умолчанию, для реалистичного планирования |

Важно: списки B, C, D не хранятся как отдельные копии таблицы — это SQL-запросы/представления (views) над Master Pool с фильтром по `tier` и `population`. Так при обновлении координат или часовых поясов правки вносятся один раз, и это автоматически отражается во всех списках.

### 2.4 Настраиваемость порога и списка стран

- Порог населения для списков A/B/C/D задаётся в конфигурационном файле, а не зашивается в код — это можно скорректировать без участия разработчика в дальнейшем.
- Список "стран, доступных для поездок" (Tier 5) — отдельная редактируемая таблица в конфигурации (страна + признак визового режима), т.к. визовые условия периодически меняются и не связаны с географическими данными.
- В настройках профиля пользователя можно указывать собственные фильтры сверху этих списков (например, ограничить список D только странами без визы) — согласуется с уже заложенным в `core/src/best_place.py` шагом фильтрации по стране/визовому режиму/часовому поясу.

## 3. Автодополнение при вводе города (поиск и подсказки)

- При вводе пользователем текста бот ищет совпадения по полям `name`, `name_ru`, `alt_names[]` начиная с первых введённых букв (префиксный поиск), а также допускает нечёткий поиск (учёт опечаток, разных транслитераций) для повышения устойчивости.
- Если совпадений больше одного (одноимённые города в разных странах/регионах — типичная ситуация), бот показывает кнопки-варианты вида "Название (Регион, Страна)", чтобы пользователь выбрал точный объект.
- Поиск выполняется по тому производному списку, который релевантен текущему сценарию (например, при выборе места для соляра в "укороченном" режиме — поиск идёт только по списку C, а не по всей базе).
- Существующий эндпоинт `GET /api/cities/search?q=...` должен быть доработан с параметром выбора списка (`list=A|B|C|D`), чтобы бот передавал нужный контекст в зависимости от текущего сценария.

## 4. Обработка отсутствующего города (Fallback-логика)

Применяется, если введённый пользователем город не найден ни в одном из списков (актуально в первую очередь для очень малых населённых пунктов, которые не попали в Master Pool).

### 4.1 Алгоритм

1. Если у пользователя есть возможность указать ближайший крупный ориентир (район, область, ближайший известный город) — предложить выбрать из списка похожих названий или ближайших крупных городов того же региона.
2. Если это не помогает, использовать геолокационный fallback: подставляется ближайший город из Master Pool **в том же часовом поясе** (это обязательное условие — часовой пояс важнее физической близости, так как влияет на точность расчёта времени).
3. Итоговые координаты для расчёта — координаты найденного заменяющего города; при этом для расчёта самого времени рождения/соляра поправка на разницу долгот между исходной точкой (если её координаты известны хотя бы приблизительно) и городом-заменителем может быть учтена как смещение в минутах (опционально, второй уровень точности).
4. Пользователю явно сообщается, что использован город-заменитель, с указанием его названия — это важно для прозрачности расчёта и доверия клиента.

### 4.2 Работа с историческими часовыми поясами

Для городов, у которых часовой пояс менялся исторически (актуально для дат рождения в СССР и ранних постсоветских годах), используется история изменений из tzdata по конкретной дате рождения, а не текущее смещение — это распространённая ошибка непрофессиональных программ, которую нужно избежать[cite:66][cite:70]. Текущий модуль `core/src/timezone_utils.py` (согласно документации, работает через `timezonefinder`) необходимо дополнить обращением к исторической таблице переходов, а не только к текущему определению пояса по координатам.
