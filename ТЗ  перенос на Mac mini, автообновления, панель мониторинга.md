# ТЗ: перенос Core/бота на Mac mini, конвейер обновлений через GitHub, панель мониторинга

## Контекст

Проект «Солярная карта» на текущий момент состоит из трёх рабочих модулей: расчётное ядро на Python/FastAPI (`core/`), MAX-бот на Node.js/TypeScript (`bot/`) и desktop-приложение на Electron (`desktop/`), при этом ядро и бот сейчас запускаются вручную через терминал на компьютере разработки. Задача — вынести ядро и бота на отдельный Mac mini как постоянно работающий сервер, наладить безопасную доставку обновлений с версионированием и откатом, и добавить визуальную панель управления состоянием сервисов.

## 1. Перенос Core и бота на Mac mini

### Цель
Максимально простой для пользователя (не разработчика) способ держать сервер "всегда включённым и работающим", без ручного набора команд в терминале при каждом перезапуске компьютера.

### Рекомендуемый подход: process manager вместо ручных терминалов

Вместо запуска `python -m uvicorn ...` и `npm run dev` в отдельных окнах терминала, как сейчас описано в инструкции, следует использовать процесс-менеджер **PM2** — он держит процессы живыми, автоматически перезапускает их при сбое и запускает при загрузке системы.[^1][^2][^3]

Схема настройки:

1. Установить Node.js и Python на Mac mini (аналог требований из текущей инструкции: Python 3.11+, Node.js 20+).
2. Установить PM2 глобально: `npm install -g pm2`.
3. Создать единый конфиг `ecosystem.config.js` с описанием двух процессов — `core` (команда запуска uvicorn) и `bot` (команда запуска Node-бота). Один файл конфигурации заменяет три терминала из текущей инструкции.
4. Запустить всё через `pm2 start ecosystem.config.js`, зафиксировать список процессов командой `pm2 save`.
5. Сгенерировать автозапуск при перезагрузке Mac mini: `pm2 startup` создаёт нужный `launchd`-агент автоматически, без ручного написания plist-файлов.[^4][^5][^1]

Это закрывает требование "максимально просто": после первоначальной настройки Mac mini достаточно просто быть включённым — PM2 сам подхватывает процессы при старте и перезапускает их при падении, ручное вмешательство не требуется.[^2][^3]

### Альтернатива (нативный вариант без PM2)
Если не хочется ставить дополнительный инструмент — можно использовать нативный `launchd` через `.plist`-файлы в `~/Library/LaunchAgents/`, которые запускаются при входе в систему и перезапускаются, если процесс упал. Этот путь более "нативен для macOS", но требует ручного написания XML-конфигов под каждый сервис — менее удобен, чем PM2, для дальнейшего расширения новыми модулями.[^5][^6][^4]

Рекомендация: использовать PM2 как основной слой управления процессами, поскольку он даёт единый интерфейс мониторинга (`pm2 status`, `pm2 logs`, `pm2 monit`) и проще интегрируется с будущей визуальной панелью через HTTP/JSON.[^7][^8]

### Сетевой доступ для вебхука MAX-бота
Поскольку продакшн-режим MAX Bot API требует публичный HTTPS-эндпоинт для вебхука (Long Polling только для разработки), для Mac mini нужно выбрать один из вариантов:
- Постоянный домен с проксированием через обратный прокси (например, Caddy или nginx) и SSL-сертификатом (Let's Encrypt).
- Туннелирующий сервис (Cloudflare Tunnel, ngrok с постоянным доменом) — проще в настройке, не требует статичного IP или проброса портов на роутере.

Рекомендуется туннель как более простой вариант для домашней сети без статического IP — это отдельная задача настройки, требующая уточнения провайдера туннеля.

## 2. Конвейер обновлений через GitHub с версионированием

### Цель
Разработка ведётся на текущем компьютере, готовые версии выгружаются на GitHub, Mac mini периодически проверяет наличие новых версий и устанавливает их, при этом старые версии не удаляются — сохраняется возможность откатиться.

### Схема выпуска версий (со стороны разработки)

1. Использовать GitHub Releases — при готовности новой версии создаётся релиз с тегом версии (например `v1.3.0`) и прикреплённым архивом (zip/tar.gz с готовым кодом core+bot).
2. GitHub Releases API предоставляет эндпоинт получения последнего релиза `GET /repos/{owner}/{repo}/releases/latest`, который отдаёт метаданные и прямые ссылки на скачивание.[^9][^10]
3. Каждый релиз содержит номер версии в имени тега — это используется для сравнения "текущая установленная версия vs последняя доступная".

### Схема обновления (со стороны Mac mini)

Скрипт-агент обновления (bash или Node.js), запускаемый по расписанию (через `cron` или встроенный таймер PM2/launchd), выполняет:

1. Запрос к GitHub API `releases/latest`, сравнение версии с локально установленной (хранится в файле `current_version.txt`).[^11][^10][^9]
2. Если версия новее — скачивание архива релиза (`curl`/`wget` по `browser_download_url` из ответа API).[^10][^12]
3. Распаковка новой версии в отдельную папку с именем версии, например `versions/v1.3.0/`, **не перезаписывая** предыдущие папки — так одновременно хранится история версий на диске.
4. Обновление символической ссылки `current -> versions/v1.3.0/` (симлинк), на которую смотрит PM2-конфиг — это позволяет мгновенно переключаться между версиями без остановки прочей структуры.
5. Плавный перезапуск процессов PM2 (`pm2 restart core bot`), чтобы подхватить новый код.
6. Запись новой версии в `current_version.txt` и лог обновления (дата, версия, статус) для последующего аудита.

### Откат к старой версии
Поскольку все версии хранятся отдельно в `versions/vX.Y.Z/`, откат — это просто переключение симлинка `current` на нужную папку и перезапуск процессов. Такую операцию стоит вынести отдельной кнопкой в визуальную панель управления (см. раздел 3), чтобы не требовать от пользователя работы в терминале.

### Рекомендация по хранению версий
Ограничить количество хранимых версий (например, последние 5-10), автоматически удаляя самые старые, чтобы диск не переполнялся — политику ротации нужно зафиксировать отдельно (сколько версий хранить).

## 3. Визуальная панель мониторинга и управления

### Цель
Единая точка, где видно состояние каждого модуля (включён / отключён / завис) и можно управлять им кнопками (включить, отключить, обновить), с расширяемостью под будущие модули.

### Архитектура панели

Панель реализуется как отдельное веб-приложение (простая страница на React/Vue или даже статический HTML+JS), обращающееся к небольшому управляющему API на Mac mini, который в свою очередь обёртывает команды PM2.

**Управляющий API (Node.js/Express или FastAPI, отдельный лёгкий сервис):**

| Эндпоинт | Действие |
|---|---|
| GET /status | Возвращает список процессов и их состояние (`online`, `stopped`, `errored`, "не отвечает") — через `pm2 jlist` в формате JSON[^1] |
| POST /start/{name} | `pm2 start {name}` |
| POST /stop/{name} | `pm2 stop {name}` |
| POST /restart/{name} | `pm2 restart {name}` |
| POST /update | Запуск скрипта проверки и установки обновления вручную |
| POST /rollback/{version} | Переключение симлинка на указанную версию + restart |
| GET /versions | Список установленных версий на диске |

PM2 предоставляет команду `pm2 jlist`, отдающую полный статус всех процессов в структурированном JSON (аналог того, что видно в `pm2 list`/`pm2 monit`), что делает интеграцию с веб-панелью прямой задачей парсинга JSON, а не разбора текстового вывода.[^8][^1]

### Определение состояния "завис"

Обычный `online`-статус процесса не гарантирует, что сервис реально отвечает — процесс может быть жив, но зависнуть (не отвечать на запросы). Поэтому статус "завис" в панели нужно определять отдельно от статуса PM2:

- Дополнительная периодическая проверка `GET /api/health` у Core-сервиса (такой эндпоинт уже реализован в текущем проекте).
- Для бота — проверка последнего успешного ответа на ping/last-seen таймстамп внутри самого бота.
- Если процесс `online` в PM2, но health-check не отвечает дольше заданного таймаута (например, 30 секунд) — статус в панели помечается как "завис" (отдельным цветом, например жёлтым/оранжевым), в отличие от "включен" (зелёный) и "отключен" (серый/красный).

### Визуальные индикаторы

| Статус | Цвет | Условие |
|---|---|---|
| Включён | Зелёный | PM2 online + health-check отвечает |
| Завис | Жёлтый/оранжевый | PM2 online, но health-check не отвечает N секунд |
| Отключён | Серый | PM2 stopped |
| Ошибка | Красный | PM2 errored / многократные автоперезапуски за короткий период |

### Расширяемость под новые модули
Панель проектируется как список карточек, а не жёстко прошитый под текущие два модуля (core, бот). Каждая карточка модуля описывается конфигурационной записью (имя процесса в PM2, health-check URL, отображаемое название) — при добавлении нового модуля достаточно добавить одну запись в конфиг панели, без изменения кода самой панели.

## 4. Итоговый список задач для разработчика

1. Настроить Mac mini: установить Python/Node, перенести код `core/` и `bot/`, настроить `.env` с токеном бота.
2. Настроить PM2 (`ecosystem.config.js`, `pm2 startup`, `pm2 save`) для двух процессов.
3. Настроить сетевой доступ для вебхука MAX (домен + SSL или туннель).
4. Написать скрипт проверки обновлений (сравнение версии через GitHub Releases API, скачивание, распаковка в `versions/vX.Y.Z/`, переключение симлинка, перезапуск через PM2), запуск по расписанию.
5. Настроить процесс публикации релизов на стороне разработки (тег версии + сборка архива + загрузка в GitHub Releases).
6. Реализовать управляющий API (обёртка над PM2 + health-check + версии + откат).
7. Реализовать веб-панель (карточки статусов, кнопки управления, история версий с кнопкой отката).
8. Настроить политику ротации хранимых версий на диске.

## 5. Открытые вопросы для уточнения

- Периодичность автопроверки обновлений на Mac mini (например, раз в час/раз в сутки).
- Способ сетевого доступа для вебхука MAX — постоянный домен с проксированием или туннелирующий сервис.
- Нужна ли панель мониторинга доступна удалённо (из любой точки) или только в локальной сети Mac mini.
- Сколько версий хранить одновременно перед автоочисткой старых.
